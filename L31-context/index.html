Solution 1 The whole idea in three lines

Context in three parts

const AuthContext = createContext<AuthContextValue | null>(null); <AuthContext value={{ session, login, logout }}>{children}</AuthContext> const auth = useContext(AuthContext);
01 · build the pass

createContext makes a place for one kind of value. null is what you get outside any provider.

02 · put the value on it

The provider: every component inside it can reach the value. React 19 writes <AuthContext>; older code writes <AuthContext.Provider>.

03 · pick it up

useContext in any component inside, at any depth. When the value changes, that component re-renders.

Say: Three parts, always. Build the pass once. Put a value on it near the top of the app. Pick it up wherever you need it. We wrap step 3 in our own hook, useAuth(), so nobody imports the context directly.

The rule

Every component that reads a context re-renders when its value changes. Keep contexts small and split them by topic.

Do: With "Two contexts": Sign in → Header and AccountPage flash. Add a dish → Header and the cards flash. Switch to "One big context", reset, and do the same: every reader flashes on every change. Footer never does: it reads nothing.

If asked: Re-rendering is usually cheap. It matters for big lists or values that change many times a second (a text field, a timer). That's when you split, or reach for a store (L32).

Solution 2 How a kitchen takes orders

The ticket rail: useReducer

The deal

Components only describe what happened. One pure function decides what the new cart is. That function is the only cook.

Say: In a kitchen, waiters don't cook. They write a ticket ("table 4: one coq au vin") and put it on the rail. The chef reads the tickets one by one and follows the house rules. In React: dispatch puts a ticket (an action) on the rail; the reducer is the chef.

Solution 2 A pure function

A reducer in four parts

function cartReducer(cart, action) { switch (action.type) { case "added": … case "removed": … } return newCart; } const [cart, dispatch] = useReducer(cartReducer, []);
01 · the state now

The cart as it is before this ticket.

02 · what happened

An object with a type: { type: "added", dish }.

03 · one case per ticket

The rules of each kind of change.

04 · a new state

A new array, never a changed old one. No fetch, no localStorage inside.

Step 5: useReducer is useState's big sibling: it gives the state and dispatch. Calling dispatch(action) makes React run the reducer and re-render with what it returns.

Pure means: same cart + same action → always the same new cart, and nothing else happens. That's why StrictMode may call it twice in development without harm.

Solution 2 The bugs of the second half

When a reducer goes wrong

Changing the old cart

cart.push({ dish, qty: 1 }); return cart;
Nothing re-renders: it's the same array, so React sees no change.
return [...cart, { dish, qty: 1 }];

A forgotten return

case "removed": cart.filter((item) => …);
error TS7029: Fallthrough case in switch. (Without the check: "removed" runs into "cleared" and empties the cart.)
case "removed": return cart.filter((item) => …);

A typo in the ticket

dispatch({ type: "add", dish })
Type '"add"' is not assignable to type '"added" | "qtyChanged" | "removed" | "cleared"'.
dispatch({ type: "added", dish })

Side effects in the reducer

localStorage.setItem("bistro.cart", …) inside the reducer
StrictMode runs reducers twice in development. A reducer must only calculate.
useEffect(() => save(items), [items]) in the provider

Quick check The chef's rules

Which line may go inside a reducer?

A reducer only calculates a new state from the old state and the action. Saving and fetching are side effects (an effect or an event handler). Pushing changes the old array, so React sees no change.
