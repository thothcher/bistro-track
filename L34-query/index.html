Solution 1 The cold room

Ask the cache, not the server

A cache outside the tree

The QueryClient is a map from a key to an answer. It lives in a module, not in a component.

A page asks by key

"Give me the answer for ["dishes","list","all"], and here is how to fetch it if you do not have it."

The cache decides

Missing or too old: it calls queryFn. Otherwise it answers at once, with no request.

Everybody shares it

Home, Menu and the dish page read one entry. Two pages that ask at the same moment share one request.

Do: One press per idea. Step 1: the cache appears outside the component tree. Step 2: three pages ask it by key, with the same key. Step 3: the cache has nothing yet, so it calls the queryFn and a request goes to the API. Step 4: the answer is stored under the key and given to all three.

Say: Compare with L32: a store holds data we own. This cache holds copies of data the server owns, and it knows how old each copy is. Same place in the map, a different tool.

Next time a page asks: the cache looks at the date on the label. Fresh: it answers at once, and no packet goes to the API. That is the whole idea; the rest of the lecture is its settings.

Solution 1 What you give, what you get

Two things in, a few flags out

const { data, isPending, isError, isFetching, } = useQuery({ queryKey: ["dishes", "list", category], queryFn: () => api<Dish[]>(path), });
01

queryKey
The address of the data in the cache. Same key, same entry. It works like a dependency array: change a value in it and you ask a new question.

02

queryFn
How to fetch it, as a function that returns a promise. Called only when the cache has no fresh answer. If it throws, the query is in error.

03

data · isPending · isError
The three states of a screen: nothing yet, something wrong, or the answer. data is undefined until it arrives.

04

isFetching
A request is running right now, for the first time or in the background. The old data stays on screen meanwhile.

Say: That is the whole API for reading data. Two inputs and a handful of flags. The rest of the options (staleTime, enabled, placeholderData…) are tuning.

Remember: in TanStack Query v5 the options go in one object. Tutorials from before 2024 pass the key and the function as two arguments, and use cacheTime, keepPreviousData and onSuccess. All of those are gone; the mistakes slide shows the TypeScript messages.

Flags: isPending means "no data yet". isFetching means "a request is running". They are different: after the first answer, a refresh has isFetching true and isPending false. isLoading is both at once: the very first request.

Solution 1 The four mistakes you will see today

When a cache goes wrong

A variable missing from the key

useQuery({ queryKey: ["dishes"], queryFn: () => fetchDishes(category) })
No error. Click Drinks and the starters stay: same key, same entry.
queryKey: ["dishes", "list", category]: everything the function uses

The cache made inside a component

function App() { const client = new QueryClient(); … }
No error. Every render makes an empty cache, so everything is fetched again.
One queryClient in its own module, imported by main.tsx

The old way of calling it (Query v4)

useQuery(["dishes"], fetchDishes) · cacheTime · onSuccess
TS2769 · Property 'queryKey' is missing in type 'string[]'. · 'cacheTime' does not exist in type 'UseQueryOptions<…>'
useQuery({ queryKey, queryFn }) · gcTime · no callbacks: use the data

No provider around the app

createRoot(…).render(<App />) // no QueryClientProvider
Error: No QueryClient set, use QueryClientProvider to set one
<QueryClientProvider client={queryClient}> in main.tsx

Say: Two silent ones and two loud ones. The silent ones are the dangerous ones: number 1 gives a page that looks fine and shows the wrong dishes. Number 2 gives a page that works and fetches on every render: only the Network tab tells.

Mistake 3: the TypeScript message is longer: it lists three overloads. The first line is the useful one. AIs and old tutorials write v4: if an AI answer uses two arguments, cacheTime, keepPreviousData: true or onSuccess, it is v4.

All the messages were produced by compiling these lines with TypeScript 6 and TanStack Query 5.104.

Solution 2 The four mistakes of the second half

When the cold room is run badly

A copy of the data in state

useEffect(() => { if (data) setDishes(data); }, [data]);
It works, until the cache refreshes: you hold an old copy, and render once more for nothing.
Use data directly, and derive what you need from it

A skeleton on isPending for a disabled query

{results.isPending && <Skeleton />} with enabled: searching
No error. A query that never ran is pending forever: the skeleton never goes away. (isLoading is false.)
isLoading, or isFetching && !data, or render it only while enabled

Thinking "stale" means broken

the default staleTime: 0, and "why does it fetch again?"
No error. Stale data is shown at once and refetched when someone looks: on mount, on focus.
Give each kind of data the staleTime it deserves: a minute for the menu, 0 for a queue

A guest's data with no guest in the key

queryKey: ["profile"]
No error. Beso signs in and sees Maia's profile: the entry is still fresh.
queryKey: ["profile", email], and queryClient.clear() on sign-out

Say: All four are silent. Number 4 is the serious one: it is a privacy bug. Number 2 is the one that wastes an afternoon: a spinner that never stops, with nothing in the console.

Flags in v5: isPending = no data yet (it covers "disabled" and "loading"); isLoading = isPending && isFetching, the first request in flight. We checked: a disabled query has isPending: true, isFetching: false, isLoading: false.

What does staleTime: 60_000 mean?
