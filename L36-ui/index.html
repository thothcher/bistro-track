Apéritif Before we start

Questions from last time?

Mutations, invalidation, optimistic updates, toasts.

01

Why invalidateQueries({ queryKey: ["orders"] }) and not refetch() in onSuccess?

refetch() refreshes one query, by name: the screen you forgot stays old. invalidateQueries says what changed, and every screen that shows it follows.

02

What does cancelQueries protect against in an optimistic update?

A refresh that was already on its way: it would land after our change and put the old status back for a moment.

03

Why does our toast have role="alert" for errors and "status" for the rest?

A screen reader reads an alert at once and a status politely, when it is free. A toast with no role is invisible to a guest who cannot see it.

Solution 1 The first rule of ARIA: if a native element does the job, use it

Use the browser's own parts first

  1. A button is a buttonIt takes the focus, answers Enter and Space, has a role and a name. A div with onClick has none of it, and the linter says so.
  2. A dialog is a dialogshowModal() does the four rules for you. We tried it in Chrome: the focus moves in, Tab stays inside, Esc closes, the focus returns, and the page behind ignores clicks.
  3. Then add what it does not giveA look, animation, a menu with arrow keys and typeahead, the same behaviour in every browser. That is where a library comes in.

Say: Before any library, the browser. A real button is free accessibility. A real dialog opened with showModal() gives you the four rules without a line of focus code. We tested it: after showModal() the focus is on the first control, Tab cycles inside, Esc closes it, and the focus returns to the button that opened it. Clicks on the page behind are blocked.

Honest detail: it is a good tool and you can use it today. The catches: styling the backdrop and animating it takes care, a menu or a toast is not a dialog, and in React you need a ref and an effect to open it. Radix, our library later, does more than dialog: arrow-key menus, typeahead, nesting, the same behaviour everywhere.

The linter: npx oxlint --jsx-a11y-plugin -D jsx-a11y reports on the first line: click-events-have-key-events ("Visible, non-interactive elements with click handlers must have one of keyup, keydown, or keypress listener") and no-static-element-interactions ("Static HTML elements with event handlers require a role"). It even suggests dialog when you write role="dialog" on a div: "Prefer dialog over role attribute dialog".

A role needs a name

A nameless dialog says just “dialog”. Which one?

aria-modal is a promise

It hides the page for the screen reader. It does not trap the keyboard.

Do: Start with everything on, then switch off one line at a time. Without role="dialog" the panel is just a div: the screen reader reads its content as plain text and never says "dialog". aria-modal: it says that the content outside is not available. It does not move or trap the keyboard focus: that is still your job, and it is the code of the previous slide.

Solution 1 The four mistakes you will see today

When the page cannot be used

A div that behaves like a button

<div onClick={open}>Your order</div>
jsx-a11y(click-events-have-key-events) · Visible, non-interactive elements with click handlers must have one of `keyup`, `keydown`, or `keypress` listener.
A <button type="button">: focus, Enter, Space, a role, a name

The ring removed, and nothing in its place

outline-none · button:focus { outline: none }
No error. A keyboard user cannot see where they are. Fine for you with a mouse, a disaster for them.
Keep it, or draw a better one: focus-visible:ring-3 focus-visible:ring-ring, and measure it

A tab order of your own

<button tabIndex={5}>Send</button>
jsx-a11y(tabindex-no-positive) · Avoid positive integer values for `tabIndex`. The button jumps the queue, in every page that uses it.
Write the elements in the order people read them. tabIndex={0} or {-1} only

A picture without words

<img src="coq-au-vin.jpg" />
jsx-a11y(alt-text) · Missing `alt` attribute. Must have `alt` prop, either with meaningful text, or an empty string for decorative images.
alt="Coq au vin", or alt="" when the text next to it already says it

Say: Two loud ones, because we switched the lint rules on, and two quiet ones. The ring (number 2) never makes a sound: nobody on the team uses a keyboard, so nobody sees it.

The messages are real: they come from npx oxlint --jsx-a11y-plugin -D jsx-a11y on a file with these four lines. The rules are not on by default in npm run lint: add the flag, or your editor's equivalent.

Remember: our own cart passed this linter with zero warnings and still failed the keyboard test. The linter finds the mistakes that can be seen in the code, which is a lot, but not all.

Solution 2 Who owns the behaviour, who owns the look, who owns the code

Three kinds of UI libraries

1 · Ready-made kits

MUI · Mantine · Ant Design

You get finished components with their own look.

You own nothing: it lives in node_modules.

The catch bending the look takes effort, and an upgrade can change your UI.

2 · Headless primitives

Radix UI · React Aria

You get behaviour and accessibility, with no style at all.

You own your markup and your CSS.

The catch you must style and assemble every part.

3 · Copy-in components

shadcn/ui

You get components generated into your project, built on a headless base and Tailwind.

You own the files: read them, change them.

The catch you maintain them: no automatic updates.

Today: number 3

Le Bistro has its own look, and we want to read every line. There is no best one: a deadline favours number 1, a brand favours number 2.

Say: Three answers to the question we just asked. Number 1: buy the whole thing, and live in its look. Number 2: take only the behaviour, and write the look yourself: a lot of work, and the best control. Number 3 is in between: the behaviour of number 2, a look already written in Tailwind, and the code lands in your project, so it is yours.

Honest detail: there is no best one. A back-office tool with a deadline is a fine home for number 1. A design system with its own brand is happy with number 2. We use number 3 because Le Bistro has its own look and we want to read every line.

shadcn's base: the CLI option -b (or --base) chooses what is underneath: radix (Radix UI, what we use), base (Base UI) or aria (React Aria). The components you write do not change.

What does asChild do, in a Button that wraps a Link?

B: Slot hands the Button's props and classes to its child, so the link keeps being a link, and looks like a button. A would be an interactive element inside another one: two Tab stops, and invalid HTML. D would break "open in a new tab".
