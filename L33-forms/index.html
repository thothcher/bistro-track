Solution 1 The rulebook

One schema, three jobs

const loginSchema = z.object({ email: z.email("Enter your email address"), password: z.string().min(1, "Enter your password"), }); type LoginValues = z.infer<typeof loginSchema>; // { email: string; password: string }
01

z.object({…})
The rules: what a valid form looks like, field by field. Plain data, written once, in one file.

02

z.email("…") and .min(1, "…")
Every rule carries the message the guest reads. The rule and its message cannot drift apart.

03

z.infer
The TypeScript type of the values, read from the schema. No second definition to keep in sync.

04

Zod 4 spelling
z.email() replaces z.string().email(), and one option, error, replaces message and required_error.

Say: Zod is a library for describing data. Today we use it for form data; later, for API answers too. A schema is data about data: it can check a value, explain what is wrong, and tell TypeScript what the value is.

Do: One part per press. For job 3, hover over LoginValues in your editor if you can: the type appears as { email: string; password: string }, and nobody wrote it.

Zod 4: z.email() is the new way; the old z.string().email() still works but is deprecated. Many tutorials still show Zod 3: the mistakes slide has the differences.

Solution 1 What you get from useForm

One hook, four things to know

const { register, handleSubmit, formState: { errors, isSubmitting }, } = useForm<LoginValues>({ resolver: zodResolver(loginSchema), defaultValues: { email: "", password: "" }, });
01

useForm<LoginValues>
Makes the form object. The type comes from the schema, and defaultValues gives every field a starting value.

02

resolver
The plug: zodResolver(schema). The form asks Zod, not the browser, whether the values are valid.

03

register · handleSubmit
What you call: register for each input, handleSubmit for the form.

04

formState
What the form knows: errors, isSubmitting, and more. Read only what the screen shows.

Say: That is the whole API we need today. There are more things in the box (watch, reset, setValue), and the documentation is good, but these four pieces build the whole lecture.

Remember: formState is a proxy: the form re-renders for a property only if you read it. Reading errors subscribes to errors; if you never read isDirty, changes to it cost nothing. That is how register keeps the renders down.

defaultValues matter: without them a field starts as undefined, and the schema says "expected string, received undefined".

Solution 1 The four mistakes you will see today

When a form goes wrong

A Zod 3 habit

z.string({ required_error: "Name is required" })
TS2769 · 'required_error' does not exist in type '$ZodStringParams'. In plain JavaScript there is no error: the option is silently ignored.
z.string({ error: "Name is required" }), or .min(1, "Name is required")

The schema as the form's type

useForm<typeof schema>({ resolver: zodResolver(schema) })
TS2322 · Type 'Resolver<{ email: string; … }>' is not assignable to type 'Resolver<ZodObject<…>>'
useForm<z.infer<typeof schema>>(…): the type of the values, not of the schema

Reading a message that may not exist

{errors.email.message}
TS18048 · 'errors.email' is possibly 'undefined'.
{errors.email?.message}: there is no error until there is one

register without the call

<input {...register} />
No error at all. The field is never registered, so the form says it is invalid however much the guest types.
<input {...register("email")} />: it is a function, call it with the field's name

Say: Three of these are loud and one is silent. The silent one is the dangerous one: nothing in the editor, nothing in the console, and the form refuses everything. If a field is always invalid, look at the register call first.

Mistake 1: Zod 4 renamed the options: one error replaces message, required_error and invalid_type_error. AIs and old tutorials write Zod 3.

Mistake 2: useForm wants the type of the values (LoginValues), which z.infer reads out of the schema. The real compiler message is longer than the one shown here: it ends in a wall of types.

All four messages were produced by compiling these exact lines with TypeScript 6, Zod 4.6 and React Hook Form 7.90.

Problem 2 Fill in step 1 and step 2, then press Back

The review sees nothing.

Each step is a component, and a component's state dies when it leaves the screen.

1 · Fill in step 1 and 2

Four seats, 20:30, a guest with a diet. Press Next each time.

2 · Press Back

3 · Read the review

Do: With "Each step keeps its own state": set 4 seats, pick 20:30, press Next, add a guest ("Anna", "no nuts"), press Next: the review says "Table of 2, arriving 19:00" and does not know about your guest. Press Back twice: step 1 has forgotten the 4 seats. Now switch to "One form above the steps" and repeat: everything survives, and the review reads it all.

Say: A step is a component, and a component's state is born when it appears and dies when it leaves. Each step also only knows its own fields, so the last step cannot read the first. The fix is the one you learned in L28: put the state above the steps. A form library does exactly that, for the whole form at once.

Problem 2 Press the button: the guest types a phone number we already know

Ask the server at every key

Nine digits, nine questions

Every key sends a request, even for "5" and "55".

The answers get mixed up

A slow answer to an old question arrives after a fast one to a new question.

The last one wins

The guest reads an answer for a number they are no longer typing.

Do: Press "Type 555123456". The number goes in digit by digit and every digit asks the server. The answers come back in a different order than they were asked, and the last one to arrive wins: it says the number is free, but it is the number of an existing account.

Say: This is the race condition from L29, in a form. Nine requests for one phone number, nine "Checking…" flashes, and a wrong answer on screen. A real server does not answer in order either: it is slower for some requests than for others.

Note: in Le Bistro the check is GET /api/v1/enterprise/validation/check-phone?number=…; it takes about 0.9 seconds and the number 555123456 is reserved as "taken". The delays in this demo are made up to show the order problem, so it does not wait for the real server.

Solution 2 The four mistakes of the second half

When the slip gets messy

The index as a key

{fields.map((field, index) => <div key={index}>…)}
The typed text still looks right (the form puts it back). What the row remembers itself does not: an open panel, the focus, an animation jump to the wrong guest.
key={field.id}: it follows the row, not the place

register on your own component

<QuantityStepper {...register("seats")} />
TS2739 · Type '{ onChange: ChangeHandler; onBlur: ChangeHandler; ref: RefCallBack; name: "seats"; … }' is missing the following properties: qty, onDecrease, onIncrease
<Controller … render={({ field }) => …} /> and use field.value, field.onChange

A number field gives text

<input type="number" {...register("seats")} /> with z.number()
Invalid input: expected number, received string. An empty field with valueAsNumber gives: expected number, received NaN.
register("seats", { valueAsNumber: true }), or a Controller with real numbers

Next and Save in one place

{last ? <button type="submit"> : <button type="button">}
No error: Next sends the form. React keeps one button and turns it into a submit button during the click.
<button key="next" …> and <button key="save" …>

Say: Number 4 is the strangest one: the form saves after step 2 and the guest has not reached the review. We found it in our own tests. Number 1 is the one AIs write most.

Mistake 1: we tested it: with key={index} and registered text inputs, the text stays correct after removing the first row, because the form writes the values back. A row that keeps its own state (an open "details" panel) shows it on the wrong guest: Beso's panel opened under Chiko.

Mistake 3: an <input> always gives a string, even with type="number".
