Solution 1 The waiter

A mutation carries a change

A query reads, a mutation changes

useMutation is the other half of the library: the same cache, a different job.

You say when

A query runs when a component needs it. A mutation runs when you call mutate().

The server answers

isPending, isError, and the callbacks onSuccess, onError, onSettled.

Then tell the cache

invalidateQueries marks what is old, and every screen that shows it asks again.

Do: One press per idea. Step 1: the button calls mutate() on the mutation. Step 2: the mutation runs its mutationFn: a request goes to the API. Step 3: the answer comes back. Step 4: onSuccess tells the cache that everything starting with "orders" is old, and the kitchen page and "My orders", both reading from the cache, refetch.

Say: The button never talks to the kitchen page. It talks to the cache, and the screens that share that cache follow. That is why a new screen with the same data needs no change in the button.

Honest detail: the cache lives in this browser. A waiter's tablet shows both the kitchen page and "My orders" and refreshes both. A guest's phone has only "My orders". A kitchen screen on another machine has its own cache: it learns about the order from its own five-second polling (L34). Invalidation does not reach other browsers.

Solution 1 What you give, what you get

Something to run, and a few flags

const send = useMutation({ mutationFn: (order: NewOrder) => api<Order>("/orders", …), onSuccess: () => { … }, }); send.mutate(order); send.isPending · send.isError · send.error
01

mutationFn
What to run: a function that returns a promise and throws on failure. It receives the variables you give to mutate.

02

mutate(variables)
Runs it now. A query runs when a component needs it; a mutation never runs by itself.

03

isPending · isError · error
The life of one call. Disable the button while it is pending; show the error if it failed.

04

onSuccess · onError · onSettled
What to do afterwards: clear the cart, show a toast, tell the cache.

Say: Compare with useQuery: there you give a key and a function and you get data. Here you give a function and you get a mutate to call. No key, because nothing is stored under it: a mutation is not cached.

v5 detail: the flag is isPending. The v4 name isLoading is gone from mutations (TypeScript says "Property 'isLoading' does not exist on type 'UseMutationResult'").

mutate or mutateAsync? mutate never throws: errors go to onError and the global handler. mutateAsync returns a promise that rejects: you must catch it. Use mutate by default.

Solution 1 The four mistakes you will see today

When a change goes wrong

Changing data, forgetting the cache

onSuccess: () => toast.success("Sent")
No error. The kitchen's screen and "My orders" stay old until their next refresh, or F5.
Add queryClient.invalidateQueries({ queryKey: ["orders"] })

A typo in the key you invalidate

invalidateQueries({ queryKey: ["order"] })
No error. Nothing starts with "order", so nothing is refreshed.
The start of the key, copied from the query file: ["orders"]

mutateAsync with no catch

await send.mutateAsync();
Uncaught (in promise) ApiError: the server said no, and nothing caught the rejection.
send.mutate() with callbacks, or wrap mutateAsync in try/catch

The old way of calling it (Query v4)

useMutation(sendOrder, { … }) · invalidateQueries(["orders"]) · send.isLoading
TS2559 · Type '() => Promise<…>' has no properties in common with type 'UseMutationOptions<…>' · TS2559 · Type 'string[]' has no properties in common with type 'InvalidateQueryFilters<…>' · TS2339 · Property 'isLoading' does not exist on type 'UseMutationResult<…>'
One options object, { queryKey }, and isPending

Solution 2 The four mistakes of the second half

When the waiter runs ahead

Optimistic, but no cancelQueries

onMutate: ({ id, status }) => { queryClient.setQueryData(…) }
No error. A refresh that was already on its way lands after your change and shows the old status for a moment.
await queryClient.cancelQueries(…) first, then change the cache

No way back

an onMutate with no onError and no onSettled
No error. The card says COOKING for ever, although the server said no.
Return { previous }, restore it in onError, refetch in onSettled

A next page that never ends

getNextPageParam: (last) => last.page + 1
No error. The list asks for page after page, past the end: hasNextPage never turns false.
Answer undefined on the last page: last.hasNext ? last.page + 1 : undefined

The old infinite query (Query v4)

useInfiniteQuery(["orders"], fn, { getNextPageParam })
TS2769 · Property 'initialPageParam' is missing in type '{ queryKey: …; queryFn: …; getNextPageParam: … }' but required in type 'UseInfiniteQueryOptions<…>'
One options object with initialPageParam: 1

Say: The first three are silent. Number 1 is the subtle one: it works nearly always, and flickers once in a while, only when a refresh is in flight. Number 3 is the classic infinite-scroll bug.

Mistake 4: the TypeScript message is long: it lists three overloads, and repeats the missing-property line under each. The line shown is the one to read. Produced by compiling this call with TypeScript 6 and Query 5.104.

What happens to the value that onMutate returns?

B: whatever onMutate returns is handed to onError and onSettled as context. That is how the snapshot of the old queue travels to the rollback. A: we write the new data ourselves, with setQueryData. C: onMutate cannot cancel the call (throwing in it fails the mutation). D: the server gets what mutationFn sends.
